## Scope vs. Vision

1. **Full scope vs. narrowing.** vision.md is a verbatim capture of `research_task.md`; there is no research_proposal.md yet to have narrowed anything. So at this stage there is no retreat to detect — the object under review is the task itself. My job is therefore to state what a *faithful, evidentiary* treatment of this exact scope requires, so that Round 2's first proposal draft can be checked against it.

2. **Deepening vs. retreat — not yet applicable**, but I flag a risk direction: the four numbered contributions in vision.md (dual-layer decision system, edge vision pipeline, RAG, PSI-gated MLOps) are stated as architecture-plus-headline-metric. The risk is that a first proposal draft will "narrow" by presenting only the polished numbers from the README's summary table and dropping the README's own caveats (the epoch-73→77 correction, the `ogretmen` data-leakage flag, the "never run in model mode" limitation, the file-read-vs-memory latency correction). Those caveats are not decoration — they are the evidentiary trail that makes this team's numbers credible. A proposal that drops them for polish would be an unjustified retreat from rigor, even though it doesn't literally cut a "topic."

3. **Vision elements not yet covered — these are research goals, not cuts:**
   - **(a) Empirical characterization of the LLM layer's actual failure/override rate.** vision.md's central thesis ("if the LLM misses a threshold, the rule engine escalates") is an architectural guarantee, not yet a measured phenomenon — the codebase confirms AQUA-1B has never been run through `eval.py` in model mode (`--rule-only` only). This is the single most important open item: it's the causal claim the whole paper is titled on, and it is currently unmeasured. Round 2 proposal MUST commit to either (i) running the model-mode eval before writeup and reporting the observed LLM/rule-engine disagreement rate, or (ii) explicitly reframing the claim as an architectural guarantee under a hypothetical LLM failure, honestly labeled as untested in production.
   - **(b) Independent cross-validation of the rule engine.** The codebase contains a `twin_bridge/` module (Modbus client + `compare.py`) that runs `backend/rules.py` against an independently-implemented IEC 61131-3 (CODESYS/PLC) safety logic on a digital twin, explicitly designed so "where they disagree, that is a finding." This is directly relevant evidence for the dual-layer safety claim (two independently-written implementations converging is real corroboration), yet it is (i) not mentioned anywhere in vision.md, and (ii) untracked in git with no result artifacts — it appears to have been built but never run to produce data. This is a vision-adjacent capability that is NOT yet covered and should become an explicit research goal for Round 2+, not silently dropped for being unfinished.
   - **(c) Full threshold sweep for RAG calibration.** vision.md states "RAG thresholding optimized for an F1 score of 0.84" but the only sweep evidence in the codebase (README) shows exactly two threshold points (0.84, 0.85). Whether 0.84 is truly the argmax of a denser sweep, or just the better of two candidates, is not yet established and should be a proposal commitment.
   - **(d) Real-world (not synthetic) drift detection episode.** PSI-gating validation to date consists of synthetic degradation injection (10%/20% confidence-shift, collapse to 0.1–0.4) plus resampling-noise controls. No live production drift event and gated retrain-cycle outcome is yet reported. This is squarely a "not yet covered" research goal, not something to quietly claim as demonstrated.

## Assessment

The system as described is a legitimate, already-deployed applied-AI artifact with an unusually disciplined engineering culture — the README documents its own past errors (a wrong checkpoint reported for months, a rule-engine copy that silently drifted from production, a PSI binning scheme that produced a false binary alarm) and how each was caught and fixed. That self-correcting posture is evidentiary gold for a rigor reviewer: it means the team has habits that surface, rather than hide, threats to validity. The core architectural claim — a small local LLM proposes, a dependency-free deterministic module (`rules.py`, importing no FastAPI/pydantic/httpx) has sole authority, severity is only ever escalated, and malformed LLM output fails safe — is a genuine and well-motivated integration pattern, and the shared-code argument (the eval harness and the production backend literally import the same `rules.py`) is closer to a real causal mechanism than a "trust the diagram" claim. That is the correct standard, and it is met here.

However, the central causal claim of the paper — that this architecture "explicitly solves the LLM unreliability problem" — currently rests on architectural guarantee, not on an observed failure trace. The codebase itself documents (in TODOS.md, P1, "before thesis") that AQUA-1B has never been run through the evaluation harness in model mode; only the rule engine has been exercised (8/8 rule-only scenarios). Separately, the agent benchmark shows the *same* production model (AQUA-1B) emits a parseable tool-calling action 0% of the time across four scripted scenarios, with a prefill test producing identical output regardless of input. Taken together, these are strong signals that AQUA-1B's practical reasoning contribution to the decision pipeline may be much smaller than the paper's framing implies, and that the "LLM proposes, rule engine catches misses" narrative has not yet been observed to occur even once with real model output. This is not disqualifying for the *system* (the safety design is sound regardless of whether the LLM is currently doing useful reasoning), but it is disqualifying for the *paper's framing* until either the model-mode eval is run and reported, or the framing is honestly rescoped to "an architectural guarantee against a model that has not yet been characterized as reliable."

On evidentiary extensiveness: several headline numbers rest on small, single-run samples with no reported variance — 40 latency frames on one device with no repeated trials or thermal-state control, 29 RAG queries against 12 hard negatives for threshold calibration, and a 98-image validation split for both mAP and export-format comparisons. None of this makes the numbers wrong, but "extensively established" in my mandate's sense (architectural reasoning + measurement + ablation/sensitivity convergence) is not yet met for any of the four headline results; each currently has one measurement and one plausible story, not corroborating lines of evidence.

## Novelty Analysis

- **Closest existing work, by component:**
  - Precision aquaculture vision: YOLO-family detectors for fish counting/behavior (multiple RAS and aquaculture CV papers, 2021–2025) — the detector itself (YOLOv11s + ByteTrack) is not novel.
  - Edge deployment: CoreML/ANE benchmarking of YOLO variants exists in general edge-AI literature; export-format accuracy-vs-latency tradeoff studies are common (though rarely done with the same held-out validation set across every export format — that methodological discipline, not the finding, is the paper's export-bench contribution).
  - LLM safety/hallucination mitigation: guardrail/rule-layer patterns over LLM outputs are an active area (constitutional AI, output validators, "LLM-as-advisor with deterministic override" patterns in fintech/medical triage). A **rule engine as sole source of truth that only ever escalates, never lowers, severity, verified via literal code-sharing between production and eval** is a specific, tighter version of this pattern than most cited guardrail work, which typically re-validates via a second model or a schema check rather than a domain rule engine with formal precedence semantics.
  - RAG calibration: precision-biased similarity thresholding to control hallucinated citations is a known idea in RAG safety literature generally, but doing it via an explicit sweep against curated *hard negatives* (not just held-out positives) and shipping a de-tuned (non-F1-optimal) threshold for asymmetric error cost is a reasonably crisp, well-motivated choice — genuinely worth stating as a design contribution rather than a component reformulation.
  - MLOps drift: PSI over model output distributions (rather than input features) for gating retraining is used in industry MLOps practice; PSI-over-confidence-deciles specifically, with quantile (not equal-width) binning chosen after observing a diagnosed false-alarm failure mode, is a legitimate, if modest, engineering contribution — the *diagnosis* of why equal-width binning failed is more novel than the PSI-gating idea itself.

- **What is genuinely new about the composition:** the paper's defensible novelty claim is the **integration discipline**, not any individual component: (1) a formally shared, dependency-free rule module enforced across production and eval paths by mutation-tested thresholds; (2) deterministic (non-LLM) tool routing in the agent layer, adopted *because* a benchmark showed the candidate LLM failed to reliably emit parseable actions; (3) an asymmetric-cost RAG threshold chosen off a positive/hard-negative sweep rather than F1 alone; (4) PSI-gated retraining with a minimum-improvement gate to avoid shipping noise-level deltas. This is a coherent "avoid over-trusting the LLM at every layer" design philosophy, consistently applied across four different subsystems. That thematic consistency, if made explicit and argued as the unit of contribution (rather than four separate component descriptions), is a legitimate, if modest, novelty claim for a systems paper.

## Logical Gaps

- **Untested central mechanism.** The "LLM proposes, rule engine catches misses" claim has never been observed with the real model (only rule-only eval has run). The paper cannot claim this dynamic as an *observed* safety net until it is.
- **The safety net may be catching nothing, because there may be nothing to catch.** If AQUA-1B mostly fails to produce a usable structured output at all (as agent-bench suggests, 0% format success), then the "rule engine overrides the LLM's severity call" pathway may rarely fire in the way vision.md implies — the more common failure mode may be "malformed output fails safe," which is a different (and lesser) claim than "reasoning model missed a threshold, rule engine caught it."
- **Adapter version ambiguity.** README/TODOS flag that the deployed LoRA adapter may still be the 8-sample v1, with the 128-sample v2 unreleased/untested. Any claim about "LLM reasoning quality" is currently attached to an adapter of unconfirmed provenance.
- **mAP/precision/recall are a single operating point.** MODEL_RAPORU.md itself notes P/R are read at the confidence value that maximizes F1 on the PR curve for one run; presenting 0.858/0.719 as fixed system properties without the PR curve or confidence-threshold context risks overclaiming precision at the expense of recall as an inherent property rather than an operating-point choice.
- **Single-species, single-tank, single-class generalization gap.** The vision model is single-class (`sturgeon`) on 510 images from what appears to be one deployment context; the paper's framing (precision aquaculture broadly) is broader than the evidence supports without an explicit generalization-scope caveat.
- **Edge benchmark generalizes across "edge AI" broadly** from one Apple Silicon device; no non-Apple edge target (Jetson) has been measured, and the TensorRT rows are explicitly absent — the paper must not imply CoreML/ANE conclusions transfer to other embedded accelerators.
- **`ogretmen` model leakage precedent.** The codebase has one clearly-diagnosed instance of a data-leaked model (train==val) whose inflated 0.925 mAP50 was correctly discarded. This is good practice, but it also means the reviewer should independently confirm (not merely take on faith) that `sure_v1`'s 412/98 split has zero image-level or video-frame-level overlap (e.g., adjacent frames from the same clip appearing in both train and val) — a much subtler leakage mode than the `ogretmen` case, and one common in video-sourced fish datasets.

## Required Ablations
(Analyses of *already collected* artifacts/logs, or artifacts obviously producible from existing code without a new field deployment.)

1. **Run `llm-service/eval.py` in model mode** (as TODOS.md #2 already prescribes) and report the full confusion pattern between AQUA-1B's raw severity judgment and the rule engine's final decision across all 8 scenarios (and ideally the 128-example fine-tune set held out). This is not optional — it is the direct evidence for the paper's title claim.
2. **Run `twin_bridge/compare.py --replay`** against at least one captured digital-twin session and report the agreement/divergence rate between `backend/rules.py` and the independent CODESYS logic, with the "expected divergence" vocabulary mapping made explicit. This upgrades the safety claim from single-implementation self-consistency to independent cross-validation.
3. **Recover and report the full RAG threshold sweep** (not just the 0.84/0.85 pair) from `rag/calibrate.py`'s output, to confirm 0.84 is the actual F1-argmax and to show the precision/recall tradeoff curve, not two isolated points.
4. **Video/clip-level split audit** of the 510-image sturgeon dataset: confirm no frame from the same source clip appears in both train (412) and val (98); report the number of distinct source videos and their train/val allocation.
5. **Repeat the CoreML/ANE latency measurement across multiple runs / times / thermal states** if raw benchmark logs or the ability to re-run `export_bench.py` exist, to report variance (not just a single p50/p95 from 40 frames) and rule out thermal-throttling or cold-cache artifacts.
6. **PR-curve / operating-point sensitivity analysis** for the vision model: report precision/recall at 2-3 alternate confidence thresholds (not just the F1-maximizing point) to make clear that 0.858/0.719 is a chosen operating point, and discuss what the recall would be at a threshold tuned for the safety-relevant "do not miss a fish" objective versus the reported default.
7. **Sample-size / CI reporting for RAG metrics**: with only 29 positive queries and 12 hard negatives, report a confidence interval or exact counts (e.g., "hit@1 = 23/29") alongside the ratio, so readers can judge precision of the estimate.
8. **Compare AQUA-1B vs AQUA-7B decision-quality**, not just agent-format-compliance, on the same 8 (or 128) scenario set, to substantiate or refute the implicit claim that the 1B on-prem model is "good enough" to be worth having in the loop at all versus being a near-inert wrapper around the rule engine.

## Alternative Explanations

1. **Edge latency advantage is a batch-size-1, single-device artifact.** *Discriminating analysis:* explicitly state batch=1 and single Apple-Silicon-device scope in the paper; do not extrapolate "CoreML/ANE wins" beyond that hardware family without the Jetson data `export_bench.py --emit-jetson` is designed to produce. *Caveat if not run:* label the edge-superiority claim "Measured on Apple Silicon (M-series) ANE only, batch=1, 40 memory-resident frames; not measured on Jetson/TensorRT."
2. **High RAG hit@1/MRR could be inflated by a small, low-overlap corpus (8 docs / 44 chunks) rather than genuine retrieval skill.** *Discriminating analysis:* the README already flags a version of this trap for the `fixed-480w` strategy (near-arithmetic hit@5); apply the same scrutiny to the chosen `heading` strategy — report corpus size, chunk count, and query-to-chunk ratio explicitly next to the metric so a reader can judge base-rate difficulty, and ideally report a random/no-retrieval baseline.
3. **The "LLM adds reasoning value" claim could be an artifact of the rule engine doing all real work, with the LLM contributing only natural-language narration.** *Discriminating analysis:* Required Ablation #1 and #8 above directly address this — without them, this alternative explanation is not ruled out and should be explicitly scoped as an open question in the writeup rather than implicitly dismissed by the architecture diagram.
4. **INT8 quantization "beating" fp32 ONNX in mAP could be run-to-run measurement noise on a 98-image validation set, not a genuine effect.** The README/MODEL_RAPORU.md already interprets this correctly (attributes it to export-path noise, not quantization benefit) — the paper must preserve this honest interpretation rather than simplifying it into "INT8 is free or better," which would overclaim.
5. **PSI drift-gating validation is entirely synthetic** (injected degradation, resampled subsets) rather than an observed real-world distribution shift. *Discriminating analysis / honest caveat:* label PSI-gating as "Measured under synthetic degradation injection on the validation reference set; not yet observed against a real production drift episode," and do not claim the retrain-gate has been exercised end-to-end in the field unless Required Ablation evidence of an actual triggered-and-evaluated retrain cycle exists.
6. **The self-corrected historical errors (epoch 73→77, PSI equal-width binning, rule-engine copy drift) could mean current numbers still contain an undiscovered analogous error.** *Discriminating analysis:* since the team has a demonstrated pattern of catching such errors via fresh `val()` reruns and mutation-tested thresholds, the writeup should include one explicit "reproducibility check" step (e.g., re-running `val()` on `best.pt` fresh at submission time) and state the exact date/commit the reported numbers were last verified against, rather than treating the numbers as static facts.

## Verdict

This raw task/vision has a real, well-motivated novel integration pattern (deterministic-final-authority safety gating, code-shared rule engine, precision-biased RAG threshold, PSI-gated retraining) and an unusually rigorous engineering culture that self-diagnoses its own errors — but the paper's title-level causal claim about the LLM layer is currently unsupported by any model-mode evaluation, and several headline metrics rest on single, small, unreplicated measurements. This is fixable without new physical deployment (mostly by running eval.py in model mode, running twin_bridge/compare.py, and recovering/reporting fuller sweep data that likely already exists in local logs), so it merits conditional acceptance to proceed to Round 2 with these gaps as explicit, tracked requirements rather than being treated as already established.
