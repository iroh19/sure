# Practical Compass — Round 1 Evaluation

## Assessment

This is exactly the kind of paper a practitioner would bookmark, provided it is written to foreground the right things. The core claim — "an LLM never gets the final word in a safety-critical loop; a deterministic rule engine is the sole source of truth and can only escalate, never downgrade, severity" — is not a toy observation. It is a design pattern that every team currently bolting an LLM onto an industrial control or monitoring loop (agriculture, HVAC, water treatment, energy, medical devices) needs and mostly doesn't have written down anywhere citable. In 2025/2026, "LLM agents making autonomous decisions in safety-critical settings" is one of the two or three most contested topics in applied AI, and most of the discourse is either hype ("agents will run the plant") or vague hand-wringing ("we need guardrails"). This system has a concrete, load-bearing answer, already running in production, with the failure mode that motivated it documented (`fish_count == 0` bug in the eval harness, where a copy of the rule logic silently drifted from `backend/rules.py` and reported green while validating nothing). That single anecdote is more persuasive to a working engineer than any amount of abstract argument about "LLM reliability," and it must not be relegated to a footnote.

The second strongest practitioner asset is the edge-export finding: fp32 ONNX and TorchScript export lose the *identical* −0.0104 mAP50 relative to the PyTorch baseline, matching to four decimal places on mAP50-95 — proving the loss is systematic (a post-processing/NMS path difference in the exported graph) rather than numerical noise, and that INT8 quantization on top of that export path is nearly free (−0.0082, actually *better* than fp32 ONNX, 5.8× smaller, and faster). "Export itself costs accuracy before quantization ever enters the picture" contradicts the default mental model most engineers carry ("fp32 export is a no-op, quantization is where you pay"), and it is backed by same-validation-split, same-methodology numbers across six configurations. This is a crystallized, falsifiable, actionable principle exactly of the kind this persona is mandated to demand — not "quantization helps," but "on this export toolchain, the post-processing path is where fidelity is lost, and INT8 rides on top of that loss for free." The CoreML/ANE number (9.0ms p50, 111 FPS, 3.5× over MPS PyTorch, tightest p95 tail) is a second concrete, timely data point for anyone shipping vision to Apple edge silicon in 2026.

Where the proposal is currently thin, as a raw task capture rather than a drafted paper, is that none of this prioritization is yet stated. The research_task.md treats the dual-layer safety architecture, the RAG numbers, the edge-export numbers, and the PSI drift-gating as four co-equal bullet points to "include and analyze." A practitioner reading four co-equal bullet points will not walk away with a changed mental model of any one of them — they'll read it as a systems demo write-up. The material to make this "timely and compelling" already exists in the repo (README.md and MODEL_RAPORU.md are considerably richer and more mechanistically argued than research_task.md itself — they contain the actual "why," e.g., why quantile-edge PSI binning was necessary after equal-width bins produced a false binary alarm, why e5-small beats tr-bert and the gap widens with chunk size because of asymmetric-retrieval training vs. sentence-similarity training). The task, at this stage, is to make sure the paper draft pulls those mechanistic explanations forward rather than re-deriving only the headline metrics from research_task.md.

## Scope vs. Vision

1. **Does the proposal address the full scope of the vision?** Broadly yes, in terms of enumerated systems — the research_task.md verbatim text lists all four contributions (dual-layer safety, edge vision, RAG, MLOps/drift) and the vision.md's "Empirical Results to include" section requires all headline numbers be present and unaltered. As a task capture, nothing has been dropped yet — there is no proposal narrowing yet because there is no proposal yet, only the raw task and the richer source material (README.md, MODEL_RAPORU.md) it was drawn from.

2. **Justified deepening vs. unjustified retreat?** Not yet applicable — round 1 has no drafted proposal to compare against the vision for narrowing. But I flag a **directional risk**: research_task.md is a *compressed* version of what the actual repo documents. It already drops several of the sharpest mechanistic findings that exist in README.md/MODEL_RAPORU.md — the equal-width-bins PSI failure mode, the asymmetric-retrieval explanation for e5-small vs tr-bert, the systematic (non-quantization) export-accuracy loss, the `ogretmen` data-leakage discovery and correction, the agent-tool-use benchmark showing AQUA-1B *cannot* emit a parseable function call (0% format, 0% selection) which is itself a first-class, citable negative result about small on-device LLMs and tool use. If the eventual paper proposal only reproduces the four headline bullets from research_task.md and does not pull these mechanistic details back in from the source material, that would be an unjustified retreat — not because the narrower paper is bad science, but because the richer, more interesting practitioner story is sitting right there in the codebase and would be cut for no reason other than research_task.md's compression.

3. **Vision elements not yet covered (research goals, not cuts):**
   - The **agent-tool-use negative result** (AQUA-1B 0% format/selection; AQUA-7B format-competent but selects one tool in 100% of scenarios, a constant-answer artifact, correctly flagged as such by `bench_agent.py`) is not mentioned in research_task.md at all, yet it directly supports the paper's central thesis ("why deterministic routing, not LLM reasoning, for tool calls") with a negative result — the single most convincing kind of evidence for that architectural choice. This must be surfaced as an explicit research/analysis target, not left implicit in "Tool routing is done via deterministic code."
   - The **corrected epoch-73-vs-77 discrepancy** (fitness-based checkpoint selection vs. headline-metric selection) is a genuine MLOps-literature-relevant finding about a common pitfall (`best.pt` selection criteria silently diverging from the metric a team thinks it's optimizing) and is not in the vision's bullet list.
   - The **eval-harness drift bug** (copied rule logic diverging from production, silently reporting green) is arguably the single best illustration of the paper's thesis and is currently absent from the required empirical results list.
   - **Known limitations** (recall 0.719 in dense frames, LoRA adapter still possibly the 8-sample v1, AQUA-1B never run through eval in model mode per TODOS.md item 2, dashboard not rendering RAG `sources` yet) are honestly documented in the repo but not mentioned in vision.md's scope. An applied-systems paper gains credibility, not loses it, by stating these as limitations/future work — omitting them would look like cherry-picking to a practitioner reviewer who reads the abstract's strong claims and then finds no limitations section.

None of this is scope creep to invent new experiments — it is scope *recovery*: pulling the mechanistic depth that already exists in this already-built, already-measured system back into the paper's required-results list, per this round's mandate to read "additional analysis of existing artifacts" as in-scope.

## Structural Recommendation

Ranked by what changes a senior ML engineer's workflow or mental model on a single read — these must be MAIN BODY, not appendix:

1. **The dual-layer rule-override mechanism + the eval-harness drift bug as its motivating anecdote.** This is the paper's thesis; put the concrete bug (copied rule logic silently drifting, "green and verifying nothing") in the Introduction as the motivating incident, not buried in a "lessons learned" appendix. This is the one finding that, if a reader takes away only one thing, should be it: *do not let any downstream harness re-implement business logic that must stay synchronized with production; import the module.*
2. **The systematic export-accuracy-loss finding** (fp32 ONNX/TorchScript both lose exactly −0.0104 mAP50, matching to 4 decimals) belongs in the main Results/Edge Metrics section, stated as a general principle before the specific CoreML win — this reframes "export loses accuracy" from folklore into a measured, mechanistically-explained (post-processing path, not precision) claim.
3. **The agent tool-use negative result** (AQUA-1B cannot emit parseable actions; AQUA-7B's 50% is a constant-answer artifact) must be promoted into the System Architecture / Results sections as direct evidence for the "deterministic routing over LLM reasoning" design decision — right now it risks being cut entirely since it's not in research_task.md's bullet list.
4. **PSI quantile-vs-equal-width binning failure mode** belongs in the MLOps results, not an appendix — it is a specific, transferable "gotcha" (any confidence/score distribution concentrated in a narrow band will produce a binary-alarm PSI under naive equal-width binning) that generalizes far beyond aquaculture.
5. CoreML/ANE latency table is a strong secondary result — main body, but after (1)-(3) in narrative weight, since "our export is fast" is a less differentiated claim than "our export methodology caught a systematic bug the field currently ignores."
6. The RAG threshold-asymmetry argument (F1-optimal 0.84 vs. shipped 0.85, because a missed document only weakens reasoning while a fabricated citation actively misinforms) is a clean, quotable principle for "precision-over-recall in RAG for high-stakes domains" — main body, stated as a general rule with the specific numbers as the instantiation.

## Strengths

- Grounded in a real, deployed, tested system with reproducible commands, CI gates, and mutation-tested threshold consistency (22 tests enforcing `SYSTEM_PROMPT ↔ knowledge/*.md ↔ backend/rules.py` agreement) — this is unusually rigorous provenance for an applied-systems paper.
- The central safety thesis (deterministic-final-authority) is not asserted, it is demonstrated via a documented failure mode it was designed to prevent.
- Edge-export benchmarking methodology (same validation split, same percentile methodology across formats, explicit refusal to fabricate unmeasured TensorRT numbers) models good practice and is itself a citable contribution about *how* to benchmark edge exports honestly.
- RAG evaluation avoids a subtle trap (flagging that the best-looking hit@5 configuration is an arithmetic artifact of large chunks, not retrieval skill) — this kind of "the naive best number is misleading and here's why" analysis is exactly what makes a benchmarking section trustworthy to practitioners who've been burned by cherry-picked leaderboards.
- Threshold selection (0.85 over the F1-optimal 0.84) is justified by asymmetric error cost, not by a single aggregate metric — a mature practitioner instinct.

## Critical Gaps

- research_task.md, as currently scoped, buries or omits the most mechanistically interesting findings (agent tool-use failure, PSI binning failure mode, eval-harness drift bug, checkpoint-selection discrepancy) in favor of four flat headline-metric bullets. As written, the required "Results" section reads as a systems report, not a set of crystallized principles.
- No stated position yet on **generalizability boundary**: every principle here (deterministic override, PSI drift gating, precision-tuned RAG threshold) is validated in one deployment, on one dataset scale (510 images, 8 knowledge documents, single fish species). The paper must be explicit that these are validated-in-this-setting findings with a stated hypothesis for why they'd transfer (e.g., "any safety-critical domain with a small number of hard numeric thresholds and infrequent regime change" ) rather than implicitly generalized.
- The agent benchmark result (AQUA-1B failing at tool calling entirely) is currently framed in source material as an implementation detail ("routing is deterministic code instead") rather than a first-class negative result with implications for the broader question of whether small on-device LLMs can be trusted with any agentic function-calling role — this is a timely, citable finding on its own and should not be treated as incidental.
- No cost/compute framing: for a "practitioner relevance" paper, stating what hardware/latency budget produced these results (edge device specs beyond "Apple Silicon," training time/hardware for YOLOv11s and the LoRA adapter) would materially strengthen reproducibility and adoption calculus. MODEL_RAPORU.md mentions "M4 Pro, ~1-2 hours" for training — this level of detail needs to make it into the paper's Experimental Setup.
- The known-limitations list (recall 0.719 in dense frames, AQUA-1B never run through eval.py in model mode, adapter possibly still v1) exists in the repo but is not yet a required element of the paper per vision.md — omitting it would read as overclaiming to any practitioner-reviewer who checks whether the authors are honest about weaknesses.

## Specific Suggestions

1. Add the eval-harness drift bug (`fish_count == 0` copy divergence) as the opening motivating anecdote in the Introduction — concretely, before stating the dual-layer architecture, show the reader the failure it prevents.
2. Add a dedicated subsection in Results (not System Architecture) titled something like "Why export costs accuracy before quantization" that walks through the four-decimal-place match between fp32 ONNX and TorchScript as evidence of a systematic post-processing-path cause, generalized as a checklist item for any team exporting a detector: measure fp32 export accuracy in isolation before attributing loss to quantization.
3. Promote `agent/bench_agent.py`'s findings (AQUA-1B 0%/0%, AQUA-7B's 50%-that-is-really-0%-because-constant-answer) into a labeled subsection under Results, explicitly framed as a negative result about small local LLMs and tool-calling reliability, and cite it as the empirical justification for the deterministic-router design decision.
4. Add explicit hardware/compute detail to Experimental Setup: training hardware and time for YOLOv11s and the LoRA adapter, inference hardware for each edge-export row, and the machine used for RAG benchmarking — practitioners judging "is this reproducible/adoptable for me" need this.
5. Add a short "Scope and Validation Boundary" paragraph (Discussion or end of Results) stating plainly: these findings are validated on a single-species, single-tank, 510-image, 8-document deployment; state the specific dimension along which the principle is expected to generalize (e.g., "the deterministic-override pattern generalizes to any domain with a small, enumerable set of hard physical thresholds; it is not validated for domains requiring softer, graded escalation logic").
6. Include the PSI equal-width-vs-quantile-binning failure explicitly as a Results finding with the concrete before/after numbers (0.06 → 1.05 jump vs. graded 0.039/0.098/0.265/8.28), stated as a transferable principle: "for any confidence-style output metric concentrated in a narrow real-valued band, use quantile-edge binning for PSI, not equal-width — equal-width binning on a narrow-band distribution turns drift detection into a binary alarm."
7. Add a short "Known Limitations" section to the Results/Conclusion (currently absent from the required structure) drawing directly from the repo's own honest limitations list (recall 0.719, LoRA adapter version, model never run through eval.py in model mode) — this is a credibility strength, not a weakness, and should be explicitly instructed as in-scope for the paper.

## Verdict

ACCEPT with the structural changes above — the underlying system and measurements are genuinely timely, mechanistically explained, and practitioner-actionable; the raw task capture just needs to pull forward the sharper findings already sitting in the codebase rather than settling for the four compressed headline bullets.
