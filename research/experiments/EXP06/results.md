   "found a fish nearby").

## ONNX-vs-TorchScript per-image detection diff (new script: `g6_onnx_torchscript_diff.py`)

Ran both exports directly (Ultralytics default conf=0.25, NMS iou=0.7 — the deployed default
operating point) against all 98 val images, greedy-matched detections by IoU, class is
single-class (sturgeon) so no class-mismatch possible.

- **Images with a "meaningfully different" outcome (different count, OR any unmatched detection,
  OR any matched pair below 0.9 IoU): 0 / 98 (0.0%)**
- Every one of the 98 images has an identical detection count between ONNX and TorchScript.
- 1,479 total matched detection pairs across the val set; **0 unmatched detections in either
  direction**.
- Matched-pair IoU distribution: **median 0.99999976, mean 0.99999948, minimum 0.99999496**
  (i.e. essentially bit-identical box coordinates, not just "high overlap").

**This is direct, strong mechanistic evidence supporting MODEL_RAPORU.md's causal claim that
ONNX and TorchScript's matching −0.0104 mAP50 loss is systematic, not coincidental independent
numerical noise from two unrelated toolchains.** The per-image agreement is far stronger than the
design's own success criterion ("high IoU-overlap agreement") anticipated — it is not merely
"high," it is functionally identical (differences of order 1e-5 in IoU, consistent with floating-
point noise in box-coordinate arithmetic, not a real detection disagreement).

**One honest caveat for the write-up**: this experiment shows ONNX and TorchScript agree with
*each other* almost perfectly — it does **not**, by itself, isolate *which specific stage* of the
shared path (NMS/box-decode specifically, vs. some other numeric difference introduced generically
by tracing/export vs. eager PyTorch execution) is the actual mechanism. Both formats are loaded
through Ultralytics' same `AutoBackend`/predictor wrapper, so "shared post-processing path" is
almost definitionally true for these two — the finding here confirms the *symptom* (systematic,
reproducible, non-coincidental loss shared identically by both non-eager formats) but a fully
isolated mechanism test would require comparing raw pre-NMS regression/objectness outputs between
pt/mps and the export formats, which was out of this experiment's scope. Recommend stating H6(c)
as "confirmed: the ONNX/TorchScript accuracy loss is a systematic, shared effect of exporting away
from eager PyTorch execution, not independent per-toolchain noise — consistent with, though not a
full isolation of, a shared post-processing/decode path" rather than an unqualified "NMS causes
the loss."

## Literature context (sources 8/9, per design doc step 5)

The observed ΔmAP50 range here (−0.0082 to −00104, i.e. 0.82–1.04 percentage points) sits at the
low end of, but within, the "normal 0.5–2.0pp calibrated band" the design doc cites from
TensorRT/INT8 quantization literature (source 9) — notable because the largest loss (−0.0104) is
from **fp32** ONNX/TorchScript, not the INT8 row, which as MODEL_RAPORU.md's own finding #2
states, is the more surprising result: INT8 quantization (−0.0082) loses *less* accuracy than
fp32 export, consistent with common GitHub-issue-thread reports (source 8) that decode/NMS-path
export mismatches, not weight precision, dominate small-model detection accuracy loss at export
time.
